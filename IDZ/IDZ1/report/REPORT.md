## 1. Условие задачи

Сад представляет собой прямоугольное клеточное поле. Часть клеток занята недоступными объектами: камнями, прудами и другими препятствиями. Два садовника обходят доступную территорию и обрабатывают клетки. Они не хотят встречаться, поэтому не могут одновременно находиться в одной клетке.

Первый садовник начинает в верхнем левом углу и обходит строки змейкой сверху вниз. Второй начинает в нижнем правом углу и обходит столбцы либо строки в противоположном порядке. Уже обработанные и недоступные клетки пропускаются. Если путь занят другим садовником, участник ожидает либо использует разрешённый обход.

Необходимо разработать консольное приложение для Linux, которое последовательно моделирует работу двух садовников. Программа должна показывать их положения, переходы, ожидания, пропуски препятствий, начало и окончание обработки, а также текущее состояние сада. Моделирование завершается после обработки всех достижимых клеток либо при невозможности продолжить обход с указанием необработанных участков.

Настраиваемые параметры: размеры и расположение препятствий, начальные позиции, маршрут второго садовника, скорости перемещения, время обработки и разрешение обходов.

## 2. Последовательная модель

Программа написана на C17. Все действия выполняются в одном процессе, одним последовательным циклом. Два садовника представлены двумя элементами массива `Gardener actors[2]`. Их одновременная работа имитируется общим модельным временем и временем окончания каждого действия. Отдельные процессы и потоки в ИДЗ № 1 не создаются.

Такт — условная единица модельного времени. Например, параметры `1 2 2` означают, что переход первого садовника занимает один такт, переход второго — два, обработка клетки — два. Если действие начинается в такт `t`, время его окончания равно `t + длительность`.

Пауза между кадрами задаётся отдельно в миллисекундах. Она позволяет наблюдать за картой и не влияет на порядок событий и результаты обработки. При одинаковых входных данных моделирование воспроизводимо: генератор случайных чисел не используется.

## 4. Данные программы

### 4.1. Параметры `Config`

`Config` хранит длительности переходов `move_ticks[2]`, длительность обработки `work_ticks`, начальные клетки `start[2]`, паузу отображения `delay_ms` и два признака: маршрут второго по столбцам `route2_columns` и разрешение обходов `detours`.

### 4.2. Сад `Garden`

`Garden` содержит размеры `rows`, `cols`, число доступных клеток `open_count`, число достижимых клеток `reachable_count`, массив клеток `cells` и признаки достижимости `reachable[2]` из старта каждого садовника.

Клетка хранится под одним индексом:

```text
индекс = строка * число_столбцов + столбец
строка = индекс / число_столбцов
столбец = индекс % число_столбцов
```

Значения клеток: `#` — препятствие, `.` — ещё не обработана, `+` — обработана. Положения садовников хранятся отдельно и накладываются на карту при выводе. Поэтому показ цифры садовника не меняет состояние самой клетки.

### 4.3. Садовник `Gardener`

Для каждого участника сохраняются его номер `id`, текущая клетка `position`, назначение перехода `destination`, время окончания действия `due_tick`, число обработанных клеток `processed`, маршрут `route` и индекс следующей цели `cursor`.

| Состояние | Значение |
| --- | --- |
| `READY` | Участник выбирает следующее действие |
| `MOVING` | Переход начат, но ещё не завершён |
| `PROCESSING` | Идёт обработка текущей клетки |
| `WAITING` | Сейчас нет разрешённого пути к очередной цели |
| `FINISHED` | Работа завершена, занимаемые клетки освобождены |

После завершения перехода или обработки участник становится `READY`. Для завершившего работу участника `position` и `destination` равны `-1`.

### 4.4. Вывод `Output`

`Output` хранит дескриптор журнала, признак ошибки вывода, признаки терминального отображения и до четырёх последних событий текущего такта. Этот небольшой буфер нужен только для отображения событий под обновляемой картой; полная история записывается в файл сразу при возникновении событий.

## 5. Ввод и проверка параметров

Входной файл задаётся единственным необязательным аргументом программы. Без аргумента используется `data/demo.txt` относительно текущей папки.

Пример демонстрационных данных:

```text
6 8
1 2 2
C 1
0 0 5 7
500
........
..#..#..
........
.#..#...
....#...
........
```

| Строка | Содержание |
| --- | --- |
| 1 | Количество строк и столбцов |
| 2 | Время перехода первого, перехода второго и обработки клетки в тактах |
| 3 | `C` — второй идёт по столбцам, `R` — по строкам; `1` — обходы разрешены, `0` — запрещены |
| 4 | Начальные координаты: строка и столбец первого, затем второго |
| 5 | Пауза между кадрами в миллисекундах |
| Далее | Строки карты из символов `.` и `#` |

Координаты начинаются с нуля. На демонстрационной карте 48 клеток, из которых 5 заняты препятствиями, поэтому доступны 43 клетки. Доля препятствий определяется самой картой: `5 / 48`, приблизительно 10,4 %.

`garden_load` открывает файл через `open` и создаёт поток чтения через `fdopen`. Затем `fscanf` читает параметры и карту. Проверяются:

- размеры от 1 до 30 по каждой стороне и наличие хотя бы двух клеток;
- длительности действий от 1 до 100 тактов;
- задержка от 0 до 1000 мс;
- корректность обозначений маршрута и обходов;
- допустимые координаты, различие стартов и отсутствие препятствий в них;
- длина каждой строки карты, допустимые символы и отсутствие лишних данных в конце файла.

При ошибке выводится сообщение в стандартный поток ошибок, файл закрывается, программа возвращает код `1`. Корректно прочитанный файл также закрывается после загрузки.

## 6. Маршруты и движение

### 6.1. Построение змейки

`gardener_init` формирует маршрут как последовательность номеров клеток. Первый участник проходит первую строку слева направо, вторую справа налево и так далее сверху вниз.

При маршруте `C` второй участник проходит правый столбец снизу вверх, следующий сверху вниз и далее справа налево. При маршруте `R` он проходит нижнюю строку справа налево, следующую слева направо и далее снизу вверх.

Для настраиваемого старта маршрут циклически сдвигается так, чтобы первой целью стала стартовая клетка. В основных примерах используются предусмотренные условием противоположные углы.

### 6.2. Достижимость

`mark_reachable` выполняет обход в ширину (BFS) по доступным клеткам из каждого старта. `neighbours` возвращает только соседей по стороне внутри карты. Препятствия в очередь не добавляются.

Клетка входит в `reachable_count`, если она достижима хотя бы из одного старта. Это позволяет отличать незавершённый обход от участка, к которому изначально нет доступа. Временное присутствие второго садовника при этой предварительной проверке не учитывается: оно не является постоянным препятствием.

### 6.3. Выбор очередной цели

`gardener_step` рассматривает очередную клетку маршрута. Если это препятствие, уже обработанная клетка или клетка, недостижимая из старта данного участника, цель пропускается с записью причины.

Если участник уже находится в целевой клетке, начинается обработка. В остальных случаях `garden_next_step` выбирает один соседний шаг. Пропуск цели не означает мгновенного перемещения: садовник сохраняет своё положение и к следующей цели идёт обычными соседними переходами.

### 6.4. Поиск пути и ожидание

При разрешённых обходах используется BFS с учётом текущих препятствий и занятых другим участником клеток. Поиск восстанавливает первый шаг кратчайшего доступного пути. В следующем такте путь при необходимости ищется заново.

Без обходов применяется простой порядок: сначала движение по горизонтали к столбцу цели, затем по вертикали к её строке. Если очередной шаг недоступен, садовник переходит в `WAITING`. Такая политика может привести к остановке даже при геометрически существующем обходном пути, поскольку обходы запрещены входными параметрами.

По обработанным клеткам разрешено проходить. Их повторная обработка запрещена.

### 6.5. Занятость клеток

Во время перехода `position` остаётся исходной клеткой, а `destination` содержит соседнюю клетку назначения. `free_cell` исключает для второго участника обе эти клетки. В момент окончания перехода `position` меняется на назначение, а `destination` сбрасывается.

У садовника в каждый момент есть одна текущая позиция. Резервирование назначения не означает вторую позицию: оно предотвращает пересечение переходов и движение двух участников навстречу друг другу по одному ребру.

## 7. Главный цикл и завершение действий

В начале каждого такта `gardener_complete` проверяет окончание текущих действий обоих садовников. Завершённый переход меняет позицию. Завершённая обработка меняет `.` на `+`, увеличивает счётчик участника и продвигает его маршрут.

Обработка засчитывается только в момент окончания действия. Если программу прервать раньше, незавершённая клетка останется необработанной.

После окончания действий выполняются следующие шаги:

1. Проверяется, обработаны ли все достижимые клетки.
2. Участники выбирают новые действия через `gardener_step`. Первый выбирающий чередуется в зависимости от чётности такта.
3. Проверяется, есть ли выполняющиеся переходы или обработки.
4. Выводится очередной кадр карты.
5. Если нет выполняющихся действий и никто не смог начать новое, обход признаётся невозможным.
6. Иначе выполняется `nanosleep` на заданную паузу и номер такта увеличивается.

Если участник исчерпал маршрут, `gardener_finish` переводит его в `FINISHED` и освобождает текущую клетку и назначение. При общем завершении эта функция вызывается для обоих участников.

## 8. Соблюдение инвариантов

| Требование | Как обеспечивается |
| --- | --- |
| Два садовника не занимают одну клетку | `free_cell` запрещает вход в позицию другого; назначение его перехода также резервируется |
| Препятствия не посещаются и не обрабатываются | Проверяются старты, препятствия пропускаются в маршруте и исключаются из поиска пути |
| Клетка обрабатывается не более одного раза | Обработанные цели пропускаются; перед завершением обработки проверяется, что клетка ещё имеет значение `.` |
| У каждого участника одна текущая позиция | Положение задаётся одним полем `position`, которое меняется только при завершении перехода |
| Завершивший работу освобождает ресурсы | `gardener_finish` сбрасывает `position` и `destination` в `-1` |

В отладочной сборке дополнительно используются `assert`: для различия текущих позиций и для проверки состояния клетки перед засчитыванием обработки. Основные ограничения реализованы логикой программы и не зависят от этих проверок.

## 9. Интерфейс и журнал

В настоящем терминале используется один обновляемый экран. Карта разделена границами клеток, сверху показаны номер такта и общий результат обработки. Первый садовник обозначается голубой `1`, второй — жёлтой `2`, обработанные клетки — зелёным `+`, препятствия — `#`.

Под картой показаны состояния участников и последние события текущего такта: начало и окончание переходов и обработки, ожидания и пропуски. Пример:

```text
[t=20] Садовник 1 ожидает путь к (0,7).
[t=20] Садовник 2 начал обработку (0,7), до t=22.
```

ANSI-последовательности используются для возврата курсора, очистки старого текста и цвета. `isatty` определяет, является ли стандартный вывод терминалом. Размер окна читается через `ioctl`; при небольшой высоте промежуточные границы и часть пояснений убираются. Для больших карт необходимо увеличивать окно. Полная история доступна в журнале независимо от количества показанных событий.

`output_print` записывает текст в стандартный вывод и журнал через `vdprintf`. `output_event` записывает каждое событие в журнал и добавляет его в небольшой буфер для терминального кадра. При перенаправлении вывода анимация и цвета отключаются, события выводятся обычным текстом. `output_control` отправляет управляющие последовательности только в терминал, поэтому в журнал они не попадают.

Файл `garden.log` открывается через `open` с флагами `O_WRONLY | O_CREAT | O_TRUNC`. Он создаётся в текущей рабочей папке; прежнее содержимое заменяется при новом запуске. В нём сохраняются параметры, события, карты, причины необработанных клеток и итог. Ошибки записи учитываются через признак `failed`.

После завершения восстанавливаются обычный экран и видимость курсора, выводятся итоговая карта и результат, а также подсказка о расположении журнала. Открытый дескриптор закрывается через `close`.

## 10. Способы завершения

| Код | Причина |
| --- | --- |
| `0` | Обработаны все клетки, достижимые хотя бы из одного старта |
| `1` | Некорректные данные либо ошибка открытия, чтения или записи |
| `2` | Участники не могут продолжить обход при заданных правилах |
| `130` | Прерывание сигналом SIGINT, в том числе Ctrl+C |
| `143` | Прерывание сигналом SIGTERM |

Обработчики SIGINT и SIGTERM устанавливаются через `sigaction`. Обработчик `stop_simulation` только записывает номер сигнала в переменную типа `volatile sig_atomic_t`. Работа с журналом и вывод не выполняются внутри обработчика.

Основной цикл замечает сигнал, прекращает моделирование, восстанавливает терминал, освобождает клетки и сохраняет результат. При невозможности продолжить обход или при прерывании перечисляются оставшиеся клетки. Для них указывается, был ли обход просто не завершён или клетка недостижима из обоих стартов.

Для изолированного участка возможен код `0`: это означает обработку всех **достижимых** клеток. Недостижимые при этом перечисляются отдельно.

## 11. Сборка и запуск

Для сборки требуются Linux, GCC, CMake не ниже 3.27 и Make. Проверка выполнена в Ubuntu через WSL2, с GCC 15.2.0 и CMake 4.2.3.

Из корня репозитория:

```bash
cmake --preset debug
cmake --build --preset debug
./build/cmake-debug/IDZ/IDZ1/gardeners IDZ/IDZ1/data/demo.txt
ctest --preset debug
```

Из папки `IDZ/IDZ1`:

```bash
cmake --preset debug
cmake --build --preset debug
./build/cmake-debug/gardeners
./build/cmake-debug/gardeners data/empty.txt
./build/cmake-debug/gardeners data/blocked.txt
./build/cmake-debug/gardeners data/isolated.txt
ctest --preset debug
```

Без аргумента из папки задания запускается демонстрационный сад. Пятый параметр в `data/demo.txt` равен `500`: заданная пауза составляет полсекунды на такт. Для быстрого запуска без анимационной задержки его можно заменить на `0`.

Для чтения журнала из той же папки:

```bash
less garden.log
```

Выход из `less` — клавиша `q`. Запуск из PowerShell:

```powershell
Set-Location 'C:\HSE\second_year\akos\IDZ\IDZ1'
.\run.ps1
```

`run.ps1` вызывает установленную Ubuntu через WSL, собирает программу и передаёт ей аргументы. В VS Code папка открывается в WSL: Ubuntu; используется пресет `debug`, Ctrl+Shift+B для сборки и F5 для запуска с GDB. Для просмотра анимации программу можно запускать непосредственно во встроенном терминале Ubuntu.

## 12. Тестовые наборы и результаты

## 13. Проверка требований и принятые ограничения

| Требование | Реализация |
| --- | --- |
| Последовательная программа на C для Linux | Один главный цикл, libc и POSIX, без потоков и обмена между процессами |
| Сведения об исполнителе, вариант и условие | Разделы 1–2 и начало отчёта |
| Отображение предметных сущностей и их взаимодействия | `Garden`, два `Gardener`, модельные состояния, занятость и резервирование клеток |
| Описание интерфейса, запуска и завершения | Разделы 9–11 |
| Информативный вывод ключевых событий | Карта, положения, состояния, переходы, ожидания, пропуски и обработка |
| Результаты выполнения в отчёте | Раздел 12 |
| Комментарии в исходниках | Пояснения к структурам, маршрутам, поиску, занятости и сигналам |
| Ввод-вывод через файловые дескрипторы | `open`, `fdopen`, `vdprintf`, `dprintf`, `close` |
| Нормальное завершение и прерывание | Проверка результата модели и обработчики SIGINT/SIGTERM |
| Сохранение журнала | `garden.log` с событиями и итогом |
| Тестовые данные и скрипт запуска | `data/`, `tests/run_tests.sh`, CTest |

Программа ограничена картами до 30×30 клеток. Для поиска пути используется обычный BFS; при `N` клетках один поиск занимает `O(N)` времени и `O(N)` дополнительной памяти. Маршруты и предварительная проверка достижимости также используют `O(N)` памяти. Сложность всего запуска зависит от числа переходов и тактов, поэтому один поиск пути не определяет время всей программы.

Сохранённый порядок целей и запрет обходов могут приводить к невозможности продолжить работу. В этом случае программа сообщает о ситуации, а не пытается самостоятельно менять входные правила. При разрешённых обходах участники ищут путь к своей очередной цели с учётом текущей занятости.

Текстовые события оставлены, поскольку они предусмотрены условием. Анимация, цвета и границы добавлены для наглядного наблюдения. В проект не включены графическое приложение, сеть, дополнительные варианты архитектуры или сложная система тестирования.
