## 1. Условие задачи

Сад представляет собой прямоугольное клеточное поле. Некоторые клетки заняты недоступными объектами. Два садовника обходят доступные клетки и обрабатывают их, но не могут одновременно находиться в одной клетке.

Первый садовник начинает в верхнем левом углу и проходит строки змейкой сверху вниз. Второй начинает в нижнем правом углу и проходит столбцы либо строки в противоположном порядке. Препятствия и уже обработанные клетки пропускаются. Если путь занят другим участником, садовник ждёт либо использует разрешённый обход.

Программа должна показывать положения садовников, переходы, ожидания, пропуски, начало и окончание обработки и состояние сада. Завершение происходит после обработки всех достижимых клеток либо при невозможности продолжить обход. Необработанные участки перечисляются с причиной.

В ИДЗ №2 каждый садовник реализован отдельным потоком pthread. В отличие от последовательной версии ИДЗ №1, длительности действий двух участников действительно перекрываются по времени.

## 3. Сущности и потоки

Рабочих потоков два: по одному на каждого садовника. Главный поток создаёт их, обновляет экран, реагирует на сигнал и ожидает завершения через `pthread_join`. Всего при работе программы существуют три потока ОС.

Оба садовника обладают самостоятельным поведением: выбирают цель, начинают действие, ждут его окончания и принимают следующее решение. Сад, препятствия и отдельные клетки собственного поведения не имеют: это общие данные, поэтому отдельные потоки для них не создаются.

| Структура | Содержимое |
| --- | --- |
| `Config` | Длительности переходов, длительность обработки, начальные клетки, маршрут второго, разрешение обходов и длительность единицы времени |
| `Garden` | Размеры, клетки, количество доступных и достижимых клеток, достижимость из каждого старта |
| `Gardener` | Номер, текущая позиция, назначение перехода, маршрут, текущая цель, состояние и число обработанных клеток |
| `Simulation` | Общая модель, два садовника, мьютекс, два объекта ожидания, флаг остановки, журнал и последние события для экрана |

Состояния участника: `READY` — выбирает действие, `MOVING` — перемещается, `PROCESSING` — обрабатывает, `WAITING` — ждёт изменения обстановки, `FINISHED` — завершил работу.

Клетки хранятся в одномерном массиве: индекс равен `строка * число_столбцов + столбец`. Значения клеток: `#` — препятствие, `.` — не обработана, `+` — обработана. Позиции садовников хранятся отдельно, поэтому цифры на экране не меняют состояние карты.

## 4. Входные данные

Путь к файлу передаётся единственным необязательным аргументом. По умолчанию читается `data/demo.txt` относительно текущей папки.

```text
6 8
1 2 2
C 1
0 0 5 7
100
........
..#..#..
........
.#..#...
....#...
........
```

| Строка | Значение |
| --- | --- |
| 1 | Число строк и столбцов |
| 2 | Длительность перехода первого, перехода второго и обработки клетки |
| 3 | `C` — маршрут второго по столбцам, `R` — по строкам; затем `1` — обходы разрешены, `0` — запрещены |
| 4 | Начальные координаты первого и второго: строка, столбец, строка, столбец |
| 5 | Длительность одной единицы времени в миллисекундах |
| Далее | Карта из `.` и `#` |

Для приведённого примера переходы занимают 100 и 200 мс, обработка — 200 мс. Значение `0` в пятой строке убирает задержки. Оно удобно для быстрых проверок; порядок событий при этом всё равно определяется планировщиком потоков. Пятая строка в этой работе задаёт именно длительность действий, а не период отрисовки последовательной модели ИДЗ №1.

Координаты начинаются с нуля. Размер каждой стороны — от 1 до 30, всего не менее двух клеток. Длительности действий — от 1 до 100 единиц, длительность единицы — от 0 до 1000 мс. Старты должны находиться на разных доступных клетках. Доля и расположение препятствий задаются непосредственно картой.

`garden_load` использует `open`, `fdopen` и `fscanf`. Числовые параметры читаются как текстовые токены и преобразуются через `strtol`: проверяются переполнение, диапазон `int` и отсутствие посторонних символов. Слишком длинные токены отклоняются целиком. Затем проверяются диапазоны параметров задачи, допустимые обозначения, старты, число символов карты и отсутствие лишних данных. При ошибке файл закрывается, выводится сообщение, возвращается код `1`.

## 5. Маршруты и поиск пути

`gardener_init` заранее составляет список целей для каждого участника. Первый проходит первую строку слева направо, вторую справа налево и так далее сверху вниз. Второй при `C` проходит правый столбец снизу вверх, следующий сверху вниз, продолжая справа налево. При `R` он проходит нижнюю строку справа налево, следующую слева направо, продолжая снизу вверх. Для настраиваемого старта список циклически сдвигается к этой клетке.

`mark_reachable` до запуска потоков выполняет обычный обход в ширину из каждого старта. `neighbours` возвращает соседние по стороне клетки внутри поля. Постоянные препятствия исключаются. В общее число достижимых входят клетки, доступные хотя бы из одного старта.

Рабочий поток пропускает цели, которые заняты препятствием, уже обработаны или недостижимы из его старта. Пропуск цели не перемещает садовника: к следующей цели он идёт обычными соседними шагами.

`garden_next_step` при разрешённых обходах ищет путь BFS с учётом текущей занятости и возвращает только первый соседний шаг. Без обходов выбирается шаг сначала по горизонтали, затем по вертикали. Если он недоступен, садовник ждёт. По уже обработанным клеткам можно проходить.

Во время перехода участник остаётся в исходной позиции и резервирует назначение. `free_cell` запрещает другому входить в обе клетки. Позиция меняется только после завершения перехода. Резервирование назначения не считается второй текущей позицией.

## 6. Синхронизация и асинхронная работа

Один `pthread_mutex_t` защищает все изменяемые данные модели: карту, позиции, состояния, счётчики, признаки остановки и сообщения. Оба рабочих потока и главный поток обращаются к ним под этим мьютексом. До создания потоков и после `pthread_join` данные доступны главному потоку без конкурирующих обращений.

Начало обработки или резервирование следующей клетки выполняются под мьютексом. Затем поток отпускает его, ждёт длительность действия и захватывает снова для фиксации результата. Поэтому долгие переходы и обработка одного участника не блокируют работу другого. Общего тактового диспетчера и принудительного чередования садовников нет.

В основной программе используются два неименованных семафора `sem_t`, по одному для ожидающего участника. Они создаются через `sem_init` с начальным значением `0`. При отсутствии пути поток отпускает мьютекс и блокируется через `sem_wait`. После изменения карты, освобождения клеток или остановки `wake_waiters` выполняет `sem_post` для нужных потоков. Это уведомления об изменении обстановки, а не ограничитель количества одновременно работающих садовников.

В программе `gardeners_cond` вместо семафоров используются `pthread_cond_t`, `pthread_cond_wait` и `pthread_cond_signal`. `pthread_cond_wait` атомарно отпускает мьютекс при блокировке и захватывает его перед возвратом.

Счётчик `revision` изменяется под мьютексом при уведомлении. В `wait_for_change` поток повторяет ожидание, пока обстановка не изменилась и остановка не запрошена. Это учитывает ложные пробуждения условной переменной и уже накопленные уведомления семафора. После пробуждения путь проверяется заново.

При уведомлении ожидающий участник помечается готовым к повторной проверке. Благодаря этому второй поток не принимает его прежнее состояние ожидания за взаимную блокировку до обработки уведомления.

Если пути нет и другой участник тоже ждёт либо уже завершил работу, продолжить выбранные маршруты невозможно. Устанавливаются код `2` и общий флаг остановки, ожидающие потоки пробуждаются. Запрет обходов может привести к такой остановке даже при геометрическом существовании другого пути, поскольку выбранные правила не разрешают его использовать.

## 7. Работа одного садовника и инварианты

`gardener_run` выбирает следующую подходящую цель. Если участник уже в ней, начинается обработка; иначе резервируется соседняя клетка и начинается переход. `action_pause` выполняет задержку без удержания мьютекса. Длинная задержка разбивается на части до 20 мс, между которыми проверяется остановка.

После ожидания под мьютексом фиксируется результат. Завершённый переход меняет позицию и освобождает прежнюю клетку. Завершённая обработка меняет `.` на `+`, увеличивает счётчик участника и продвигает маршрут. Прерванная обработка не засчитывается. После изменения вызывается `wake_waiters`.

| Инвариант | Обеспечение |
| --- | --- |
| Садовники не занимают одну клетку | Проверка позиции и назначения второго, резервирование под общим мьютексом |
| Препятствия не посещаются и не обрабатываются | Проверка стартов, пропуск целей с `#`, исключение препятствий из поиска |
| Клетка обрабатывается не более одного раза | Проверка `+`, исключительная занятость позиции и запись результата под мьютексом |
| У участника одна позиция | Одно поле `position`; назначение хранится отдельно до завершения перехода |
| Завершивший работу освобождает клетки | Перед выходом `position` и `destination` устанавливаются в `-1` |

Дополнительные `assert` проверяют состояние клетки перед засчитыванием обработки и различие позиций. Корректность основного алгоритма обеспечивается проверками и мьютексом, а не только отладочными утверждениями.

## 8. Вывод и журнал

Главный поток обновляет карту примерно раз в 50 мс. Частота отрисовки не управляет действиями рабочих потоков. Используются границы клеток, голубая `1`, жёлтая `2`, зелёные обработанные клетки `+` и препятствия `#`. Под картой видны состояния и последнее событие каждого участника. Для большой карты следует увеличить окно терминала.

`event` вызывается под мьютексом, поэтому сообщения участников не перемешиваются. Каждое событие записывается в `garden.log` с номером садовника, координатами и временем от запуска в миллисекундах. Отражаются переходы, ожидания, пропуски, начало и конец обработки и освобождение клеток.

При перенаправлении стандартного вывода программа печатает события и итог обычным текстом. В терминале используется отдельный обновляемый экран ANSI. Управляющие последовательности в журнал не записываются. При завершении обычный экран и курсор восстанавливаются.

Журнал открывается через `open` с `O_WRONLY | O_CREAT | O_TRUNC`. Вывод использует `dprintf` в файловые дескрипторы. В журнале остаются исходная карта, события, итоговая карта, результат и причины необработанных клеток. Он находится в папке запуска, содержимое заменяется при следующем запуске.

## 9. Завершение и сигналы

Когда обработаны все достижимые клетки, выставляется остановка и пробуждаются ожидающие. Если участник исчерпал маршрут, он также освобождает свои клетки и уведомляет второго. Главный поток вызывает `pthread_join` для созданных потоков, затем уничтожает семафоры либо условные переменные, мьютекс и закрывает журнал.

| Код | Причина |
| --- | --- |
| `0` | Обработаны все достижимые клетки |
| `1` | Ошибка данных, файлов, запуска потоков или выполнения |
| `2` | Обход невозможно продолжить при заданных правилах |
| `130` | SIGINT, в том числе Ctrl+C |
| `143` | SIGTERM |

Перед созданием рабочих потоков главный блокирует SIGINT и SIGTERM через `pthread_sigmask`. Рабочие наследуют блокировку. После создания главный восстанавливает свою маску, поэтому эти сигналы обрабатываются им. Обработчик только сохраняет номер в `volatile sig_atomic_t`; не обращается к мьютексу, семафорам, условным переменным или журналу.

Основной цикл главного потока замечает сигнал, под мьютексом устанавливает остановку и пробуждает ожидающих. Рабочие выходят из ожидания или задержки, не засчитывают прерванную обработку и освобождают клетки. Главный дожидается их и сохраняет результат.

Для всех оставшихся клеток выводится, не завершён ли обход либо они недостижимы из обоих стартов. Код `0` допускает наличие таких недостижимых клеток: условие требует обработать все достижимые.

## 10. Сборка и запуск

Используются C17, libc, POSIX и pthread. Сборка проверена в Ubuntu/WSL2 с GCC 15.2.0 и CMake 4.2.3. Нужны GCC, CMake не ниже 3.27 и Make. Ручного Makefile нет, CMake создаёт его в папке сборки.

Из папки `IDZ/IDZ2`:

```bash
cmake --preset debug
cmake --build --preset debug
./build/cmake-debug/gardeners data/demo.txt
./build/cmake-debug/gardeners_cond data/demo.txt
ctest --preset debug
```

Без аргумента используется `data/demo.txt`. Для другого сценария можно указать `data/empty.txt`, `data/blocked.txt` или `data/isolated.txt`. Журнал читается командой `less garden.log`, выход — `q`.

Из корня репозитория используются та же сборка и другие пути запуска:

```bash
cmake --preset debug
cmake --build --preset debug
./build/cmake-debug/IDZ/IDZ2/gardeners IDZ/IDZ2/data/demo.txt
./build/cmake-debug/IDZ/IDZ2/gardeners_cond IDZ/IDZ2/data/demo.txt
```

В VS Code проект открывается через WSL: Ubuntu с пресетом `debug`. Для F5 выбирается «ИДЗ2: семафоры» или «ИДЗ2: условные переменные». Настройки есть и для папки задания, и для корня репозитория.

В PowerShell из папки задания:

```powershell
.\run.ps1
.\run.ps1 -Cond -InputFile data/empty.txt
```

Один shell-скрипт проверяет обе программы через CTest. В проекте нет тестового фреймворка или зависимости от Python. Временные папки удаляются после проверок. Длительность единицы времени в обычных тестах уменьшается до 1 мс, чтобы сохранить перекрытие действий и ускорить запуск.

| `interrupt` | SIGINT и SIGTERM до окончания обработки: коды `130` и `143`, обработка не засчитана, клетки освобождены, журнал сохранён |

Для обеих версий прошли 18 из 18 тестов. Сборка и общий запуск CTest из корня репозитория также прошли: 25 из 25, включая семь тестов ИДЗ №1. Время событий и распределение работы между садовниками могут отличаться между запусками: это следствие асинхронного выполнения.

Вне сдаваемого проекта дополнительно проверены:

- AddressSanitizer и UndefinedBehaviorSanitizer на сценариях обеих версий и карте шириной 30 клеток: ошибок не обнаружено;
- ThreadSanitizer на сценариях обеих версий: гонок данных не обнаружено;
- 200 разных карт для каждой версии, всего 400 запусков: соблюдение маршрутов, соседства переходов, занятости и отсутствия повторной обработки;
- фактическое наличие трёх потоков ОС и начало двух обработок до окончания первой;
- SIGTERM во время блокирующего ожидания и SIGINT во время обработки: потоки завершаются, ожидающий пробуждается;
- по 20 некорректных входов, вариантов запуска и ошибок файлов для каждой программы;
- обновление терминального экрана, цвета, восстановление курсора и отсутствие ANSI-кодов в журнале.

Эти проверочные инструменты не включены в проект и не нужны для его сборки и использования. Проверки не являются доказательством корректности для всех входов.
